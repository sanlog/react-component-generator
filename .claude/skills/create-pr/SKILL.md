# create-pr

현재 브랜치를 기본 브랜치로 보내는 PR을 만든다. 이 스킬은 분리된 컨텍스트(fork)에서 실행되어 이전 대화를 알지 못한다. 그래서 PR 내용은 대화가 아니라 **git 기록(커밋, diff)과 코드**에서만 도출한다. 사용자가 PR 생성을 요청한 것 자체가 승인이므로 별도 확인 없이 진행하고, 끝나고 결과를 보고한다.

## 절차

### 1. 사전 점검

아래를 병렬로 실행한다.

- `git branch --show-current` — 현재 브랜치
- `git status --short` — 커밋되지 않은 변경
- `git remote -v` — 원격 존재 여부
- `gh repo view --json defaultBranchRef -q .defaultBranchRef.name` — 기본(base) 브랜치. 실패하면 `main`을 가정한다.
- `gh auth status` — GitHub 인증

다음 경우에는 PR을 만들지 않고 이유와 해결 방법을 보고하고 멈춘다.

- 현재 브랜치가 base 브랜치와 같다. PR은 서로 다른 브랜치 사이에서만 만들 수 있다. 브랜치를 만들어 작업하라고 안내한다. 브랜치 생성은 사용자가 정할 일이므로 임의로 만들지 않는다.
- `gh` 인증이 안 되어 있거나 원격이 없다.
- base 대비 커밋이 0개다 (`git log <base>..HEAD`가 비어 있음). 올릴 내용이 없다.

커밋되지 않은 변경이 있으면 PR에 포함되지 않는다. 이를 보고에 적고, 커밋은 하지 않는다(커밋은 commit 스킬의 일이다).

### 2. 변경 내용 분석

PR에 담길 범위는 `<base>..HEAD`다. `origin/<base>`가 있으면 그것을 base로 쓴다. 아래를 실행한다.

- `git log <base>..HEAD --format='%h %s%n%b'` — 포함될 커밋
- `git diff <base>...HEAD --stat` — 변경 규모
- `git diff <base>...HEAD` — 실제 변경. 크면 파일별로 나누어 읽는다.

파일명만 보고 쓰면 목적을 놓친다. 코드를 읽고 "무엇이 달라졌고 왜 필요한가"를 파악한다. 커밋 메시지는 힌트일 뿐 diff와 어긋나면 diff를 따른다. 테스트 파일이 있으면 어떤 동작을 검증하는지 읽어 테스트 섹션의 근거로 쓴다.

비밀값 의심 파일(`.env`, 키·토큰, `*.pem`)이 diff에 있으면 PR을 만들지 않고 알린다. 푸시하면 되돌리기 어렵다.

### 3. 제목과 본문 작성

**템플릿 선택.** 템플릿은 `references/`에서 관리하며 언어별로 두 개다. 저장소 이름으로 고른다.

- `gh repo view --json name -q .name` 결과가 `react-component-generator`이면(이 프로젝트) `references/pr-template.ko.md`를 쓰고, 제목과 본문을 한국어로 쓴다.
- 그 외 저장소이거나 이름을 확인할 수 없으면 `references/pr-template.en.md`를 쓰고, 제목과 본문을 영어로 쓴다.

선택한 템플릿을 읽어 그 구조를 그대로 채운다. 템플릿을 읽지 않고 임의 구조로 쓰지 않는다. 리뷰어가 PR마다 같은 위치에서 같은 정보를 찾게 하려는 것이다. 템플릿 안의 `해당 없음`/`N/A` 표기는 선택한 템플릿의 언어를 따른다.

제목 형식은 커밋과 같다: `타입: 요약`(feat, fix, refactor, chore). 한국어 템플릿이면 한국어로, 영문 템플릿이면 `type: summary` 형태로 영어 명령형 현재 시제로 쓴다. 50자 안팎, 마침표 없음. 커밋이 하나면 그 메시지를 기반으로 하고, 여러 개면 전체를 아우는 한 줄로 쓴다. 타입은 변경의 지배적인 성격으로 고른다.

본문 작성 원칙:

- 확인하지 않은 것을 사실처럼 쓰지 않는다. 테스트를 실제로 돌렸다면 결과를, 돌리지 않았다면 돌리지 않았다고 쓴다. 필요하면 테스트 명령(`package.json`의 scripts, `AGENTS.md`)을 찾아 실행해 결과를 반영한다.
- 변경 파일 목록을 나열하지 않는다. GitHub이 이미 보여준다. 대신 리뷰어가 알아야 할 맥락(왜, 어떤 선택, 주의할 점)을 쓴다.
- 해당 없는 섹션은 지우지 말고 템플릿이 정한 표기(`해당 없음` 또는 `N/A`)로 쓴다. 구조가 고정되어야 리뷰어가 빠르게 훑는다.

### 4. 푸시와 PR 생성

1. 브랜치가 원격에 없거나 로컬이 앞서 있으면 푸시한다: `git push -u origin <현재 브랜치>`. 강제 푸시(`--force`)는 하지 않는다.
2. 이미 같은 브랜치의 열린 PR이 있으면(`gh pr view`가 성공) 새로 만들지 않고 그 URL을 알린다. 사용자가 본문 갱신을 원하면 `gh pr edit`로 처리한다.
3. 본문은 heredoc으로 전달해 줄바꿈과 특수문자가 깨지지 않게 한다.

```bash
gh pr create --base <base> --title "타입: 요약" --body "$(cat <<'EOF'
<템플릿을 채운 본문>
EOF
)"
```

세션 지침(system-reminder)에 PR 본문 attribution 줄이 있으면 본문 맨 끝에 그대로 붙인다. 이 스킬은 fork에서 실행되므로 해당 지침이 보이지 않을 수 있다. 그 경우 임의로 만들어 붙이지 않는다.

### 5. 보고

- 생성된 PR의 URL, 제목, base와 head 브랜치
- PR에 포함된 커밋 목록
- 실행한 검증과 결과(실행하지 않았다면 그 사실)
- PR에 포함되지 않은 커밋 전 변경, 건너뛴 단계

## 하지 않는 것

- 커밋 생성, 브랜치 생성·삭제, `--force` 푸시, base 브랜치로의 직접 푸시.
- 사용자가 요청하지 않은 리뷰어 지정, 라벨, 머지(`gh pr merge`).
- 초안(draft) 여부를 임의로 정하지 않는다. 사용자가 draft를 원한다고 했을 때만 `--draft`를 붙인다.
