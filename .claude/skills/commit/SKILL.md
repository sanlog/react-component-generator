# commit

변경사항을 읽고, 의미 단위로 나누고, 컨벤션에 맞는 한국어 메시지를 만든 뒤 **별도 승인 없이 바로 커밋한다.** 사용자가 커밋을 요청한 것 자체가 승인이다. 대신 무엇을 어떻게 커밋했는지는 끝나고 빠짐없이 보고한다.

## 절차

### 1. 변경사항 분석

먼저 저장소 상태를 파악한다. 아래를 병렬로 실행한다.

- `git status --short` — 변경·신규·삭제 파일 목록
- `git diff` — 아직 스테이징하지 않은 변경
- `git diff --staged` — 이미 스테이징된 변경
- `git log --oneline -10` — 이 저장소의 기존 메시지 톤 확인

git 저장소가 아니면(`fatal: not a git repository`) 커밋할 수 없다고 알리고 멈춘다. 저장소를 새로 만드는 것은 커밋과 다른 결정이므로 `git init`은 사용자가 요청할 때만 한다.

변경이 없으면 "커밋할 변경사항이 없습니다"라고 알리고 끝낸다.

diff가 크면 파일별로 나누어 읽는다. 파일명만 보고 분류하면 한 파일 안에 섞인 목적을 놓친다.

비밀값 의심 파일(`.env`, 키·토큰이 들어간 파일, `*.pem` 등)이 변경 목록에 있으면 커밋 대상에서 빼고 사용자에게 알린다. 한 번 커밋되면 히스토리에서 지우기 어렵다.

### 2. 논리적 단위로 분류

"이 변경을 한 문장으로 설명할 수 있는가"를 기준으로 묶는다. 한 문장에 "그리고"가 들어가면 나눈다.

- 목적이 다른 변경은 따로 커밋한다. 예: 버그 수정과 스타일 개선, 기능 추가와 의존성 업데이트
- 같은 목적을 위해 함께 바뀐 파일(컴포넌트 + 그 테스트 + 스타일)은 한 커밋으로 묶는다. 쪼개면 중간 커밋이 깨진 상태가 된다.
- 한 파일에 서로 다른 목적의 변경이 섞여 있으면 하나의 커밋으로 묶고, 최종 보고에 그 사실을 적는다. 대화형 도구(`git add -p`)는 이 환경에서 쓸 수 없다.
- 변경이 작고 목적이 하나면 억지로 나누지 않고 커밋 하나로 한다.

### 3. 한국어 커밋 메시지 작성

형식:

```
타입: 요약

(필요할 때만) 본문 — 무엇을 왜 바꿨는지
```

타입은 아래 중에서 고른다.

| 타입 | 쓰는 때 |
|------|---------|
| feat | 사용자가 체감하는 새 기능 |
| fix | 버그 수정 |
| refactor | 동작은 같고 구조만 개선 |
| chore | 빌드·설정·의존성·문서 등 코드 동작과 무관한 작업 |

위 네 가지에 딱 맞지 않으면 기존 `git log`에서 쓰던 타입(`style`, `docs`, `test` 등)을 따른다. 저장소의 관례가 이 표보다 우선한다.

요약 작성 원칙:

- 한국어로, 50자 안팎의 한 줄. 마침표는 붙이지 않는다.
- "무엇을 했는지"보다 "무엇이 달라졌는지"가 드러나게 쓴다. `수정`, `변경`, `업데이트` 같은 말만 쓰지 않는다.
- 어미는 명사형 또는 "~추가", "~수정", "~개선"처럼 간결하게 통일한다. 기존 로그의 어미를 따른다.
- 본문은 요약만으로 이유가 전달되지 않을 때만 쓴다. 쓴다면 "왜"를 중심으로 한두 문장.

예시:

- 변경: 로그인 실패 시 에러 메시지가 표시되지 않던 문제 수정 → `fix: 로그인 실패 시 에러 메시지가 보이지 않던 문제 수정`
- 변경: 전체 UI를 레트로 데스크톱 스타일로 개편 → `feat: 레트로 데스크톱 테마로 전체 UI 개편`
- 변경: 중복된 날짜 포맷 함수를 하나로 합침 → `refactor: 날짜 포맷 함수 통합`
- 변경: eslint 설정 파일 수정 → `chore: eslint 규칙 정리`

### 4. 바로 커밋

승인을 기다리지 않고 커밋 단위마다 순서대로 실행한다.

1. 해당 커밋의 파일만 이름으로 지정해 스테이징한다 (`git add <파일들>`). `git add -A`/`git add .`은 비밀 파일이나 다른 단위의 변경을 끌어들일 수 있어 쓰지 않는다.
2. 메시지는 heredoc으로 전달해 줄바꿈과 특수문자가 깨지지 않게 한다.
3. 세션 지침(system-reminder)에 커밋 attribution 줄이 있으면 본문 맨 끝에 그대로 붙인다. 없으면 임의로 만들어 붙이지 않는다.

```bash
git commit -m "$(cat <<'EOF'
feat: 요약

본문(선택)

<세션 지침이 요구하는 attribution 줄>
EOF
)"
```

모든 커밋이 끝나면 `git log --oneline -n <커밋 수>`와 `git status --short`로 결과를 확인하고, 아래를 보고한다. 승인 단계가 없는 만큼 사용자가 결과를 한눈에 검토할 수 있어야 한다.

- 만들어진 커밋 목록(해시, 메시지)과 각 커밋에 포함된 파일
- 제외한 파일과 그 이유(비밀값 의심 파일 등)
- 남은 변경사항

잘못 커밋했다면 `git reset --soft HEAD~N`으로 되돌릴 수 있다고 함께 안내한다.

## 하지 않는 것

- `git push`, 브랜치 생성·삭제, `--amend`, `--no-verify`, 훅 우회. 사용자가 따로 요청하지 않으면 하지 않는다.
- pre-commit 훅이 실패하면 우회하지 않고 원인을 보고한다. 훅이 파일을 고쳤다면 변경 내용을 확인한 뒤 새 커밋으로 처리한다.
- 기본 브랜치(`main`/`master`)에서도 사용자가 요청했으므로 그대로 커밋한다. 다만 보고에 현재 브랜치를 적는다.
