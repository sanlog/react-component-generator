# TDD Rule

> **경고: 이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 프로젝트 규칙 우선

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선한다.**
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- 비즈니스 로직
- API (핸들러, 요청/응답 처리)
- 유틸 함수
- **버그 수정** (재현 테스트를 먼저 작성해 실패를 확인한 뒤 고친다)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

경계가 모호하면 **TDD를 적용한다.**

## RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인한다.** 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 실패, 오타로 인한 실패는 RED가 아니므로 테스트를 고쳐 다시 실행한다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 지금 테스트가 요구하지 않는 기능, 옵션, 추상화는 넣지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과**하는 것을 실행해서 확인한다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green을 유지한다.** 리팩터링 후 테스트를 다시 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 복사해 두기 모두 포함한다. 보고 베끼면 테스트가 코드를 따라가게 된다.

## 변명 차단표

| 변명 | 반론 |
|------|------|
| 너무 단순해서 테스트 불필요 | 단순한 코드는 테스트도 30초면 쓴다. 단순하다고 믿은 코드가 가장 자주 깨진다. 테스트가 없으면 이후 변경에서 그 단순함을 지킬 수단이 없다. |
| 나중에 테스트를 추가하겠다 | 나중에 쓴 테스트는 구현을 보고 쓰므로 통과하도록 편향된다. 실패를 본 적 없는 테스트는 아무것도 증명하지 못한다. 그리고 "나중"은 오지 않는다. |
| 시간이 없다 | 테스트 없는 코드는 디버깅과 회귀 수정으로 더 많은 시간을 쓴다. 시간이 없을수록 되돌아가는 비용이 큰 방식은 피해야 한다. |
| 삭제하면 낭비다 | 매몰 비용 오류다. 이미 쓴 코드의 가치는 검증되지 않은 상태라는 것이다. 테스트 주도로 다시 쓰는 건 보통 빠르고, 검증 안 된 코드를 유지하는 비용이 더 크다. |
| 프로토타입이다 | 프로토타입은 자주 그대로 프로덕션이 된다. 버릴 코드라면 테스트 없이 써도 되지만, 그 경우 **코드를 실제로 버려야 한다.** 남길 코드라면 TDD를 적용한다. |
